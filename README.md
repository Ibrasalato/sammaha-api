# Sammha API — سمّها

الخادم (Back end) لمنصة **سمّها لأسماء الإبل الدولية**، التابعة للمنظمة الدولية للإبل.
الواجهة (React) في المستودع [`Ibrasalato/sammaha`](https://github.com/Ibrasalato/sammaha).

- **ASP.NET Core 10** (LTS)، Web API و SignalR
- **SQL Server** عبر **EF Core 10**
- **Clean Architecture**
- يُنشر على **IIS** أو أي خادم Windows/Linux

## البنية (Clean Architecture)

```
src/
  Sammha.Domain          الكيانات وقواعد الأعمال الثابتة ومطابقة الأسماء العربية — بلا أي اعتماديات
  Sammha.Application     منطق المنصة كاملًا بنمط CQRS عبر MediatR:
                         Features/<المجال>/  أوامر (ICommand) واستعلامات (IQuery) ومعالجاتها
                         Engine/             محرك المزايدة والتسوية والمحفظة والمطابقة والإشعارات
                         Common/             المنافذ (Interfaces) و DTOs وسلوك تسجيل لكل طلب
                         يعتمد على Domain فقط (+ تجريدات EF Core للاستعلام)
  Sammha.Infrastructure  تنفيذ المنافذ: SQL Server و EF Core والترحيلات والأقفال،
                         وwebhooks لـ n8n، وبوابة ميسّر، وتشفير كلمات المرور، وتعبئة البيانات
  Sammha.Api             العرض: Controllers ترسل الأوامر والاستعلامات عبر ISender، و JWT و SignalR والخدمة الدورية ومعالجة الأخطاء
tests/
  Sammha.Tests           اختبارات وحدة واختبارات تكامل كاملة على SQL Server حقيقي
```

مثال: `POST /api/me/requests` ← `MeController` يرسل `CreateRequestCommand` ← `RequestHandlers` (في `Features/Requests`).
MediatR مثبّت على الإصدار 12.5 (آخر إصدار برخصة Apache 2.0؛ الإصدارات 13 وما بعدها تحتاج مفتاح ترخيص تجاري).

اتجاه الاعتماد للداخل فقط: `Api → Application → Domain`. و`Infrastructure` تنفّذ منافذ `Application`.
وطبقة `Api` هي نقطة التركيب الوحيدة التي تربط الطبقات.

**منافذ الطبقة Application** (في `Common/Interfaces.cs`):

| المنفذ | الغرض |
|---|---|
| `IAppDbContext` | الوصول للبيانات وفتح المعاملات مع أقفال `sp_getapplock` |
| `IPostCommit` | آثار جانبية لا تُنفَّذ إلا بعد نجاح المعاملة |
| `ICurrentUser` | المستخدم الحالي |
| `IPasswordHasher` | تشفير كلمات المرور |
| `ISmsSender` | إرسال رموز التحقق |
| `IWebhookPublisher` | إرسال الأحداث إلى n8n |
| `IPaymentGateway` | بوابة الدفع (ميسّر) |
| `ITokenIssuer` | إصدار رموز JWT |
| `IAuctionRealtime` | تحديث صفحات المزاد مباشرة |

## ما يغطيه الخادم

| المجال | التفاصيل |
|---|---|
| **الحسابات** | تسجيل، ثم دخول على خطوتين (كلمة مرور ثم رمز تحقق؛ الرمز الثابت `4321` لحين ربط مزود الرسائل)، وبوابة موظفين منفصلة، وتغيير الجوال والبريد برمز تحقق |
| **طلبات الشعارات** | ثلاثة أسماء في الطلب، ومطابقة فورية (تطابق تام أو تشابه)، وضمان 50 ريال، وإلغاء الطلب أو سحب اسم مع استرداد الضمان |
| **الفئات** | فردي (بكار وقعدان) ومنقية |
| **لجنة الاعتماد** | مراجعة كل اسم، ورفض أو إلغاء الطلب، وجدولة المزادات |
| **المزادات** | زيادة دنيا، وتمديد عند المزايدة في آخر دقيقتين، ومزايدة تلقائية حتى حد أقصى، وقائمة متابعة مع تذكير قبل البداية والنهاية بساعة، وتسوية تلقائية، وتحديث مباشر عبر SignalR (`/hubs/auctions`) |
| **الفواتير والشهادات** | فاتورة إلكترونية شاملة الضريبة 15%، وخصم الضمان، وشهادة برمز `SMC-XXXXXXXX` يتحقق منها أي أحد |
| **الاسم المركب** | يُسجَّل باسم المالك مباشرة عند الاعتماد |
| **استثمار الاسم** | حتى 3 أسماء، ورسوم دراسة 100 ريال غير مستردة، و30% لصاحب الاسم من قيمة البيع قبل الضريبة، ولا يزايد صاحبه، وإن لم يزايد أحد يؤول الاسم إليه |
| **بيع اسم** | إعادة البيع في المزاد: يُعلن قبل 72 ساعة، ومدته 3 أيام، وضمان دخول للمزايدين، وعمولة 10%. والبيع الفوري: يُعرض 72 ساعة، وعمولة 15%. ويصل ثمن البيع للبائع في محفظته بعد العمولة |
| **المحفظة والدفع** | محفظة، ودفع بالبطاقة عبر ميسّر (webhook مع منع التكرار)، ووضع محاكاة للتطوير |
| **الشكاوى والبلاغات** | رقم متابعة `BL-YYNNNN`، ومتابعة برقم الجوال، وردود الموظفين، وإيميلات عبر n8n |
| **الإشعارات** | داخل المنصة، وتُرسل إلى n8n بعد نجاح المعاملة (لإرسال الرسائل النصية أو واتساب) |
| **الصلاحيات** | مالك، ولجنة، ومدير؛ ومدير النظام الرئيسي محمي من التعديل |

الأمان:
- كل عملية مالية أو مزايدة تتم داخل معاملة SQL مع أقفال مرتّبة تمنع التداخل وتمنع الصرف المزدوج.
- محاولات رمز التحقق محدودة.
- تحديد معدل الطلبات على الدخول والنماذج العامة.
- مبلغ الدفع يُقرأ دائمًا من قاعدة البيانات، لا من المتصفح.
- الواجهة العامة لا تكشف الملاك أو المبالغ إلا بالأسماء المختصرة.

## التشغيل محليًا

المتطلبات: .NET SDK 10 و SQL Server (أو Docker).

```bash
docker run -e ACCEPT_EULA=Y -e MSSQL_SA_PASSWORD='Sammha_dev_2026!' -p 1433:1433 -d mcr.microsoft.com/mssql/server:2022-latest
dotnet run --project src/Sammha.Api
# http://localhost:5180/health
```

في بيئة التطوير:
- تُنشأ قاعدة البيانات تلقائيًا، وتُعبّأ بيانات تجريبية بنفس حسابات الواجهة: المالك `0500000001`، واللجنة `0500000002`، وكلمة المرور `123456`، ورمز التحقق `4321`.
- الدفع بالبطاقة في وضع محاكاة.

لتشغيل الواجهة على هذا الخادم: في مستودع الواجهة ضع `VITE_API_URL=http://localhost:5180` في ملف `.env.local`.

## الإعدادات (`appsettings.json`)

لا تضع الأسرار في الملف. ضعها في متغيرات البيئة على IIS، أو في `dotnet user-secrets`:

| المفتاح | الوصف |
|---|---|
| `ConnectionStrings:Sammha` | اتصال SQL Server |
| `Jwt:Key` | مفتاح توقيع الدخول، **32 حرفًا على الأقل** |
| `SuperAdmin:InitialPassword` | كلمة مرور أول دخول لحساب `ibrasalato@gmail.com` |
| `Cors:Origins` | نطاقات الواجهة المسموحة |
| `Payments:Simulate` / `MoyasarSecretKey` / `WebhookSecret` | الدفع عبر ميسّر |
| `Otp:FixedCode` / `Otp:AllowFixedCode` | حاليًا الرمز ثابت (4321) مؤقتًا. عند ربط مزود SMS على خادم المنظمة: احذف `FixedCode` واجعل `AllowFixedCode` = false واضبط `Integrations:SmsWebhookUrl`؛ الخادم يرفض التشغيل برمز ثابت خارج التطوير ما لم يُسمح صراحة |
| `Integrations:*` | روابط n8n: الإشعارات، الرسائل، إيميلات الشكاوى، الفواتير |
| `Platform:*` | قواعد الأعمال: الضمان، والسعر الافتتاحي، والعمولات، والمدد، والنسب |

في متغيرات البيئة يُستبدل `:` بـ `__`، مثل `Jwt__Key`.

## قاعدة البيانات والترحيلات

- **إنشاء ترحيل:** شغّل سير العمل **Add EF Core migration** من تبويب Actions. يولّد الترحيل في `src/Sammha.Infrastructure/Data/Migrations`، ويولّد سكربت SQL قابلًا لإعادة التشغيل في `db/sammha.sql` لمدير قاعدة البيانات.
- **عند التشغيل:** تُطبَّق الترحيلات تلقائيًا ما دام `Database:MigrateOnStartup=true`. لتطبيقها يدويًا، أوقفها ونفّذ `db/sammha.sql`.

## النشر على IIS

1. ثبّت **ASP.NET Core 10 Hosting Bundle** على الخادم.
2. حمّل الملفات المنشورة من آخر تشغيل لـ CI (الأداة `sammha-api-iis`)، أو ابنها بنفسك: `dotnet publish src/Sammha.Api -c Release -o publish`.
3. أنشئ موقعًا في IIS يشير إلى المجلد، واجعل Application Pool على **No Managed Code**.
4. أضف متغيرات البيئة للتطبيق: `ConnectionStrings__Sammha`، و`Jwt__Key`، و`SuperAdmin__InitialPassword`، وإعدادات ميسّر.
5. فعّل **WebSockets** في IIS ليعمل التحديث المباشر.
6. في ميسّر، اجعل رابط الـ webhook `https://<api-domain>/api/payments/moyasar/webhook`، وقيمة `secret_token` مساوية لـ `Payments:WebhookSecret`.

## Swagger

- الواجهة: `https://<server>/swagger` ، والوثيقة: `/openapi/v1.json`.
- للتجربة: نفّذ `POST /api/auth/signin` ثم `POST /api/auth/signin/complete` (الرمز التجريبي 4321 في بيئة التطوير)، وانسخ `token` إلى زر **Authorize**.
- تُعطَّل في الإنتاج بالإعداد `Swagger__Enabled=false` إن رغبت.

## JWT

- رمز وصول (Access token) صالح 15 دقيقة (`Jwt:AccessMinutes`) ورمز تجديد (Refresh token) صالح 30 يومًا (`Jwt:RefreshDays`) يُخزَّن مُجزّأً (SHA-256) في جدول RefreshTokens.
- `POST /api/auth/refresh` يدوّر الرمز؛ وإعادة استخدام رمز قديم تُلغي جلسات تلك العائلة كلها.
- `POST /api/auth/signout` يلغي الرمز، ومع `everywhere: true` يخرج من كل الأجهزة.
- تغيير كلمة المرور أو الدور أو إيقاف الحساب يغيّر SecurityStamp فتسقط كل الرموز السابقة فورًا.
- المفتاح `Jwt__Key` (32 حرفًا على الأقل) يوضع في متغيرات البيئة على IIS ولا يُحفظ في المستودع.

## SignalR (التحديث اللحظي)

الـ Hub على `/hubs/auctions` (WebSockets، مع رجوع تلقائي إلى SSE / Long Polling).

| من العميل | الوظيفة |
|---|---|
| `Join(auctionId)` / `Leave(auctionId)` | متابعة صفحة مزاد |
| `JoinLobby()` / `LeaveLobby()` | متابعة قائمة المزادات |

| من الخادم | المحتوى |
|---|---|
| `auction` | `AuctionDto` محدَّث (السعر، عدد المزايدات، المتصدر مُقنَّع، وقت الانتهاء، النتيجة) |
| `changed` | معرّف المزاد (للعملاء القدامى) |
| `notification` | `NotificationDto` يصل لصاحبه فقط (تمت المزايدة عليك، فزت، …) |

- الدخول اختياري: الزائر يتابع المزادات، والمسجّل يرسل رمز الوصول في `?access_token=` فتصله تنبيهاته.
- عند الاتصال يُتحقق من SecurityStamp وحالة الحساب، فالرمز القديم بعد تغيير كلمة المرور أو الإيقاف يُرفض.
- الإرسال يتم بعد اعتماد المعاملة (IPostCommit)، ولا يُفشل الطلب إن تعذّر.
- على IIS: فعّل ميزة **WebSocket Protocol** في Windows Features. ولأكثر من خادم استخدم Azure SignalR أو Redis backplane.

## الإعدادات

**إعدادات المنصة** (لمن لديه صلاحية «إعدادات المنصة» أو «سياسة الأمان»): `GET`/`PATCH /api/admin/settings`
- **التحديث جزئي:** تُرسل الحقول المراد تغييرها فقط، وكل تغيير يُسجَّل في `GET /api/admin/settings/history`.
- **استقبال طلبات الملاك:**
  - الحقول: `requestsOpen` (الشعارات)، `compoundOpen` (الاسم المركب)، `resaleAuctionOpen` (إعادة البيع بالمزاد)، `instantSaleOpen` (البيع الفوري)، `investmentOpen` (استثمار الاسم).
  - لكل خدمة رسالة اختيارية تظهر للملاك عند إيقافها.
  - إيقاف أي خدمة يرفض الطلبات الجديدة بحالة 403، ولا يؤثر على الطلبات القائمة والمزادات الجارية.
- **إعدادات عامة:**
  - إيقاف التسجيل (`signupOpen`)، وشريط إعلان، وبيانات التواصل.
  - وضع الصيانة: يتوقف للملاك تقديم الطلبات والمزايدة والدفع والبيع، ويرجع الخادم 503. اللجنة والإدارة تعمل كالمعتاد.
- **سياسة الأمان:**
  - أقل طول لكلمة المرور.
  - قفل الدخول بعد عدد من المحاولات الخاطئة لمدة محددة.
  - مهلة خمول تُخرج الموظفين من لوحة التحكم.
  - `POST /api/admin/settings/sign-out-everyone`: يُخرج كل المستخدمين من كل الأجهزة، ما عدا من نفّذه.
- **الرسوم والقواعد:** تبقى في `Platform` بإعدادات الخادم، وتظهر في اللوحة للاطلاع فقط.
- **الإعدادات العامة للزوار:** `GET /api/settings`

**إعدادات كل مستخدم:**
- `GET`/`PUT /api/me/preferences`: إيقاف رسائل SMS وواتساب لكل فئة، وهي: تمت المزايدة عليك، التذكيرات، النتائج والاسترداد، قرارات اللجنة. التنبيه داخل المنصة يصل دائمًا.
- `GET /api/me/sessions` و`DELETE /api/me/sessions/{id}`: الأجهزة المسجّل دخولها، وإخراج جهاز منها.
- `GET /api/me/security`: آخر دخول وعدد الأجهزة.

## الأدوار والصلاحيات

- **الصلاحيات:** 21 صلاحية في `Domain/Permissions.cs`، مثل مراجعة طلبات الشعارات والتحكم في المزادات وإنشاء مستخدم والرد على التذاكر. القائمة بأسمائها العربية في `GET /api/admin/permissions`.
- **الأدوار:**
  - `GET`/`POST /api/admin/roles`، و`PUT`/`DELETE /api/admin/roles/{id}`.
  - الدور الأساسي «لجنة الاعتماد» لا يُحذف، والدور الذي عليه موظفون لا يُحذف.
- **إسناد الدور:** `PUT /api/admin/users/{id}/staff-role`. مدير النظام يملك كل الصلاحيات دائمًا.
- **منع التصعيد:**
  - لا يمنح أحد صلاحية لا يملكها.
  - إنشاء مدير نظام أو ترقية حساب إليه أو تعديل حسابه لمدير النظام فقط.
- **الفحص:** كل نقطة في لوحة الموظفين تفحص صلاحيتها (`Access.RequireAsync`)، والواجهة تُخفي ما لا يملكه الدور.

## التحكم في المزادات

- `GET /api/admin/auctions?state=active|live|scheduled|paused|ended|cancelled|all&type=`
- `POST /api/admin/auctions/pause`، و`resume`، و`extend` (`minutes` من 1 إلى 43200)، و`cancel` (`reason` مطلوب).
- **النطاق:** `{ ids: [...] }` لمزادات محددة، أو `{ all: true, type? }` لكل المزادات الجارية والقادمة أو لنوع واحد.
- **النتيجة:** `{ affected, skipped: [{ id, name, reason }] }`.
- **الإيقاف المؤقت:**
  - يمنع المزايدة والمزايدة الآلية والترسية والتذكيرات.
  - الاستئناف يعيد مدة التوقف إلى نهاية المزاد، وإلى بدايته إن أُوقف قبل أن يبدأ.
- **الإلغاء:**
  - مزاد طلب الشعار يعود اسمه إلى قائمة الجدولة.
  - مزاد إعادة البيع يُلغى عرضه ويُرد ضمان الدخول للمزايدين.
- **التنفيذ:** كل مزاد يُعدَّل تحت قفله، ويصل إشعار `auction_update` للمزايدين والمتابعين، ويُسجَّل الإجراء في سجل التغييرات.

## توزيع الشكاوى والبلاغات

`GET`/`PUT /api/admin/ticket-routing`
- **المسؤولون:** يُحدَّد لكل نوع (شكوى، بلاغ، استفسار، اقتراح) الموظفون المسؤولون عنه. التذكرة الجديدة تُسند لأقلهم تذاكر مفتوحة، ويصل إشعار لكل المسؤولين.
- **البريد:** لكل نوع بريد مستقل (حتى 10)، ويُرسَل في حقل `teamTo` مع حدث البريد.
- **قصر الرؤية:** `restrictToHandlers` يقصر رؤية كل موظف على أنواعه والتذاكر المسندة له.

## تسجيل مالك الإبل

- **التسجيل:** `POST /api/auth/signup`.
- **البيانات المطلوبة:**
  - رقم الهوية، وهو للدخول.
  - الاسم الرباعي، وتاريخ الميلاد (18 سنة فأكثر)، والجنس.
  - الجنسية، وبلد ومدينة الإقامة.
  - الجوال مع كود البلد، والبريد، وكلمة المرور.
- **رقم الهوية:**
  - المواطن السعودي: 10 أرقام تبدأ بـ 1.
  - المقيم في السعودية: 10 أرقام تبدأ بـ 2.
  - غيرهما: هوية وطنية أو جواز من 5 إلى 20 حرفًا ورقمًا.
- **الدخول:** بالهوية أو الجوال (المحلي أو الدولي) أو البريد.
- **بعد التسجيل:** رقم الهوية والاسم لا يُعدّلان، والتصحيح عبر الدعم.
- **استكمال الحساب من لوحة المالك** (`profile.completion` و`profile.missing`):
  - `PUT /api/me/address`: البلد، والمدينة، والحي، والرمز البريدي (أرقام)، والشارع، ورقم تواصل آخر.
  - `POST /api/me/email/verify` ثم `POST /api/me/email/verify/confirm`: توثيق البريد برمز.
  - `PUT /api/me/personal`: للحسابات القديمة التي سُجّلت قبل النموذج الجديد.

## تدقيق الشعارات وتقرير الشعارات

- **تدقيق الشعارات** (`requests.audit`): `GET /api/admin/requests/audit?status=&type=`
  - يعرض كل اسم مطلوب مع ما يطابقه أو يشبهه في السجلات.
  - نوع العلاقة: مطابق، أو بـ«ال» وبدونها، أو مذكر ومؤنث، أو جمع، أو مفرد، أو مشابه.
  - لكل اسم سعر البيع أو السعر الحالي، و`topPrice` = أعلى سعر لشعار مشابه.
  - الجمع والمفرد يُكتشفان بحروف الجذر (`NameMatcher.SameForms`)، مثل صقر/صقور وغزال/غزلان وسلطان/سلاطين.
- **تقرير الشعارات** (`reports.marks`): `GET /api/admin/reports/marks?type=&state=&from=&to=`
  - كل مزاد برقمه التسلسلي (`AU-1001` فما بعد).
  - يضم الطلب والمالك والفائز وقيمة الفوز والفاتورة والشهادة.

## بيانات العملاء (CRM)

- **القائمة** (`owners.view`): `GET /api/admin/owners`
  - الهوية والاسم والجنسية والجوال، والشعارات مقسمة حسب الفئة.
  - رقم الهوية والجوال يظهران مخفيين جزئيًا، إلا لمن لديه `owners.full`.
- **الطباعة والتصدير** (`owners.full`): `POST /api/admin/owners/report` يسجّل الإجراء في سجل التغييرات.

## الحساب البنكي والمحافظ والضمانات

- **مدقق الآيبان:** `GET /api/banks/check-iban?iban=`
  - يتحقق من الطول حسب الدولة ومن خانات mod-97.
  - يحدد البنك السعودي من رمزه.
- **حساب المالك البنكي:**
  - `GET`/`PUT /api/me/bank-account` مع شهادة الآيبان: PDF أو PNG أو JPG حتى 5 ميجابايت، ويُفحص الملف بمحتواه لا بامتداده.
  - أي تعديل يعيد الحساب إلى «بانتظار الاعتماد».
- **الاسترداد إلى البنك:**
  - المالك يطلب الاسترداد عبر `POST /api/me/withdrawals`، ويلزمه حساب بنكي معتمد.
  - يُخصم المبلغ من المحفظة فور الطلب، ويُعاد إليها إن رُفض الطلب.
- **الإدارة المالية:**
  - **اعتماد الحسابات** (`banks.verify`): `/api/admin/bank-accounts`، مع عرض الشهادة والاعتماد أو الرفض.
  - **المحافظ** (`wallets.view`): `/api/admin/wallets` مع الأرصدة والكشف.
  - **الاسترداد** (`wallets.refund`): `/api/admin/withdrawals/{id}/complete` برقم الحوالة، أو `reject`، أو `POST /api/admin/wallets/{id}/refund` للاسترداد المباشر.
  - **التسوية** (`wallets.adjust`): `POST /api/admin/wallets/{id}/adjust` مع سبب إلزامي.
  - **الضمانات** (`deposits.view` و`deposits.refund`): `GET /api/admin/deposits` و`POST /api/admin/deposits/refund`.
    - تشمل ضمانات الطلبات وضمانات دخول مزادات إعادة البيع.
    - لا يُرد ضمان المتصدر قبل انتهاء المزاد، ورسوم دراسة الاستثمار غير مستردة.
- **التسجيل والإشعار:** كل إجراء مالي يُسجَّل في سجل التغييرات، ويصل المالك إشعار به.

## سجل النشاط (Logs)

- **الصلاحية:** `logs.view`، ويُمنح لمدير النظام تلقائيًا ولأي دور يُسند إليه.
- **ما يُسجَّل:** كل أمر (Command) يمر عبر `ActivityBehavior`، سواء نجح أو فشل بخطأ متوقع، ويشمل محاولات الدخول الفاشلة بمعرّف مقنّع.
- **كل سجل يحفظ:**
  - التاريخ والوقت.
  - المستخدم ودوره، و«عن» المالك إن كان مفوضًا.
  - الإجراء والقسم والتفاصيل والنتيجة وسبب الفشل.
  - IP والمتصفح والجهاز.
- **ما لا يُسجَّل:** كلمات المرور، ورموز التحقق، والرموز المميزة، والآيبان، ومحتوى الملفات.
- **الكتابة:** في نطاق DI مستقل، فلا يُحفظ أي تغيير لأمر فشل مع سجله.
- **العرض:** `GET /api/admin/activity?from=&to=&category=&role=staff|owner|delegate&q=&failed=&page=&size=`
- **سجل المالك:** `GET /api/me/activity?who=me|delegates|as_delegate&from=&to=&category=&q=&failed=`
  - يعرض للمالك إجراءاته، وإجراءات المفوضين على حسابه، وإجراءاته مفوضًا عن غيره.
  - لا يحتاج صلاحية موظف، ولا يراه المفوض داخل جلسة التفويض.

## تفويض إدارة الحساب

- **إضافة المفوض:** يضيف المالك مفوضًا (حتى 5 تفويضات سارية) بالبيانات التالية:
  - الاسم الرباعي ورقم الهوية والجوال والبريد.
  - الصفة: وكيل شرعي، أو فرد من العائلة، أو موظف أو مدير أعمال، أو شريك، أو أخرى مع وصفها.
  - مدة التفويض: دائم، أو مؤقت بتاريخ بداية ونهاية لا تتجاوز 3 سنوات.
  - الصلاحيات:
    - `requests`: طلبات الشعارات.
    - `invest`: استثمار الاسم.
    - `bids`: المزايدة والشراء.
    - `payments`: المحفظة والفواتير.
    - `sales`: بيع الأسماء.
    - `tickets`: الشكاوى والاستفسارات.
- **ربط الحساب:** يرتبط التفويض بحساب المفوض بمطابقة الهوية والجوال. إن لم يكن له حساب يبقى «بانتظار حساب المفوض» ويرتبط تلقائيًا عند تسجيله.
- **الجلسة المفوَّضة:** `POST /api/auth/act-as` يصدر جلسة صاحبها المالك، وفيها المطالبة `dlg`.
  - يتحقق `DelegationGuardBehavior` من صلاحيات التفويض في كل أمر.
  - تبقى لصاحب الحساب وحده: كلمة المرور والجوال والبريد، والحساب البنكي والاسترداد، والبيانات الشخصية، وإدارة التفويض.
  - كل إجراء يُسجَّل باسم المفوض «عن» المالك.
- **العودة والإلغاء:** `POST /api/auth/act-as/stop` يعيد المفوض إلى حسابه. إلغاء التفويض أو انتهاء مدته ينهي الجلسة المفوَّضة وتجديدها فورًا.
- **المسارات:** `GET /api/delegation-scopes`، و`GET`/`POST /api/me/delegations`، و`PUT /api/me/delegations/{id}`، و`POST /api/me/delegations/{id}/revoke`، و`GET /api/me/delegated`.

## شهادات التسجيل ثنائية اللغة

- **الطلب والإصدار:** `POST /api/me/certificates` بالمدخلات `{ scope: "mark" | "portfolio", reservedNameId?, ownerNameEn? }`.
  - تصدر فورًا برقم تسلسلي `SC-YYYY-NNNNNN`.
  - تشمل شعارًا واحدًا أو كل شعارات المالك، حتى 500 شعار.
  - حدّ الإصدار 30 شهادة يوميًا لكل مالك، وتتطلب إكمال البيانات الشخصية.
  - المفوض لا يصدر شهادات، لأنها لصاحب الحساب فقط.
- **محتوى الشهادة:** لقطة من الشعارات وقت الإصدار، فيها لكل شعار:
  - الاسم بالعربية واللاتينية.
  - الفئة وتاريخ القيد ورقم القيد في السجل.
  - طريقة الاقتناء.
  - وتشمل الشهادة كذلك:
    - اسم المالك بالعربية، واسمه بالإنجليزية كما في الجواز، ويُحفظ في `User.FullNameEn`.
    - الهوية مخفية إلا آخر 4 أرقام.
    - الجنسية.
- **التوقيع:** رمز توثيق HMAC-SHA256 من 16 حرفًا على كل محتوى الشهادة.
  - المفتاح من `Certificates:SigningKey`، أو يُشتق من `Jwt:Key` إن لم يُضبط.
  - يُطبع الرمز على الشهادة ويحمله رمز QR.
- **التحقق العام:** `GET /api/certificates/issued/{number}?s={code}`.
  - يعرض حالة الشهادة اليوم، مقارنةً بالسجل:
    - `valid`: سارية.
    - `partial`: انتقلت ملكية بعض أسمائها.
    - `superseded`: لم يبقَ أي منها باسم المالك.
    - `revoked`: ملغاة.
  - ويبيّن هل رمز التوثيق مطابق. لا يعرض رقم الهوية.
- **صفحات المالك:** `GET /api/me/certificates` و`GET /api/me/certificates/{number}`.
- **الموظفون:**
  - `certificates.manage`: `GET /api/admin/certificates` و`GET /api/admin/certificates/{number}` و`POST /api/admin/certificates/{id}/revoke` مع سبب. يصل المالك إشعار بالإلغاء.
  - `names.latin`: `PUT /api/admin/names/{id}/latin` لتصحيح الكتابة اللاتينية لاسم. القيمة الفارغة تعيد الكتابة التلقائية.

## الأسماء بالحروف اللاتينية

- **التحويل التلقائي:** `Transliterator` يحوّل الأسماء العربية إلى حروف لاتينية، مثل «الهيلع» → Al-Hayla' و«الصارم» → Al-Sarim.
  - يعتمد على أوزان أسماء الإبل الشائعة وقائمة بكتابات معروفة.
  - يطابق قواعد الواجهة في `src/lib/translit.ts`.
- **في الاستجابات:** `ReservedNameDto.Latin` و`AuctionDto.Latin`. يُستخدم تصحيح الموظفين إن وُجد، وإلا الكتابة التلقائية.
- **البحث:** `GET /api/names?q=` يقبل البحث بالحروف اللاتينية، مثل `al-sharahat` أو `sharahat`. البحث لا يتأثر بالأحرف الكبيرة والصغيرة ولا بـ«Al-» أو الشَرطة أو الفاصلة العليا.

## نقل البيانات من المنصة السابقة

أداة تشتغل مرة واحدة على السيرفر، وتنقل بيانات قاعدة سمّها القديمة إلى القاعدة الجديدة. القاعدة الجديدة هي `ConnectionStrings:Sammha` في نفس الإعدادات، والأداة تقرأ القاعدة القديمة بس ولا تكتب فيها.

```bash
# 1) فحص: أحجام الجداول، وطريقة قراءة كل قيمة في الجداول المرجعية (بدون أي بيانات شخصية)
dotnet Sammha.Api.dll legacy inspect --source "Server=.;Database=sammah;Trusted_Connection=True;TrustServerCertificate=True" --map-out legacy-map.json
# 2) تجربة: تنفيذ كامل داخل transaction ثم تراجع، وطباعة تقرير بالأعداد والحالات المحتاجة مراجعة
dotnet Sammha.Api.dll legacy import --source "…" --map legacy-map.json
# 3) الحفظ الفعلي (يوم النقل، بعد إيقاف المنصة القديمة)
dotnet Sammha.Api.dll legacy import --source "…" --map legacy-map.json --commit
```

- **الأعضاء:**
  - كلمات المرور القديمة (ASP.NET Identity) تشتغل كما هي.
  - الجوال يتوحد بصيغته، والمكرر منه ياخد رقم مؤقت `L-{id}` للمراجعة.
  - البريد الفاضي أو المكرر يتحط مكانه بريد مؤقت.
  - المحظور في Black_List أو الموقوف يتنقل حسابه غير مفعّل.
  - الآيبان يتنقل «بانتظار التحقق».
- **الطلبات:**
  - رقم الطلب `SM-{رقمه القديم}`.
  - نوع الشعار:
    - «منقية» = المنقية.
    - فردية + ذكر = القعدان.
    - فردية + أنثى = البكار.
  - حالة كل اسم مقترح بتيجي من C_Order_Status.
  - الضمان (فاتورة 1) بيتحدد إنه مسترد لو له فاتورة 3 مرتبطة أو عليه علامة استرداد، ومصادَر لو صاحبه فاز وما سددش.
- **المزادات:**
  - رقم المزاد `AU-{رقمه القديم}`، ومعاه كل المزايدات.
  - المستثمر ونسبته بيتنقلوا مع المزاد.
  - المزاد اللي لسه شغال بيكمل في المنصة الجديدة بضمان دخول.
  - ضمانات المزايدين (فاتورة 2) بتتنقل بحالتها.
- **الفائز ومصير الشعار:**
  - لو سدد (فاتورة 4) ⇐ الشعار ملكه، وفاتورته مدفوعة.
  - لو سجّل رسوم اسم مستثنى (فاتورة 8) ⇐ الشعار ملك اللي دفع.
  - لو ما سددش والاسم مستثنى أو انسحب أو فاتورته ملغاة ⇐ الشعار ملك **المنظمة الدولية للإبل**.
  - غير كده ⇐ فاتورة غير مدفوعة بمهلة سداد كاملة تبدأ من يوم النقل، وبعدها تتصادر تلقائيًا.
- **الأسماء المركّبة** المدفوعة بتتنقل وتترتبط بالاسم الأساسي للمالك.
- **المحفظة:**
  - حركات الشحن (6) والاسترداد (3) بتتنقل سجل تاريخي.
  - بعدها قيد تسوية واحد، عشان الرصيد يساوي `WalletAmmount` بالظبط.
- **الإشعارات** بتتنقل بتواريخها وحالة القراءة.
- **التكرار:**
  - كل سجل بيتحفظ رقمه القديم في `LegacyLinks`، فتشغيل الأداة مرة تانية ما بيكررش حاجة.
  - الترقيم الجديد بيكمل بعد أكبر رقم قديم.
- **ما بيتنقلش:**
  - حسابات الموظفين، لأنها بتتعمل من جديد.
  - **PaymentCard**، لأن فيه أرقام بطاقات وCVV ممنوع تخزينها حسب PCI DSS، والمفروض يتمسح من القديم.
  - السجلات وجداول المهام.
  - الفواتير من نوع 7 و9.
- **لاحقًا:** صور الشعارات (Name_Logo) وشرايح الإبل (MemberCamels) وجدول Request.

## نقل ملكية اسم

1. **طلب المالك:** المالك يطلب نقل اسم يملكه لمالك تاني مسجَّل، عن طريق جواله. المنصة بتعرضله الاسم مخفي جزئيًا عشان يتأكد إنه الشخص الصح.
2. **رسوم النقل:** قيمتها في الإعدادات تحت `TransferFee`، و0 معناها مجاني. بتتدفع بالبطاقة بس.
3. **موافقة المستلم:** المستلم يوافق على الطلب أو يرفضه.
4. **قرار اللجنة:** اللجنة تعتمد النقل أو ترفضه، وده بصلاحية `names.transfer`. ولو الطلب ما كملش، الرسوم بترجع لمحفظة المالك.
5. **بعد الاعتماد:** الاسم بيتسجل باسم المستلم، والمصدر بيبقى `transfer`. الشهادات القديمة اللي فيها الاسم بتظهر «لم تعد سارية»، واللوجو القديم بيتشال.
6. **المنع:** الاسم المعروض للبيع، أو اللي عليه مزاد قائم، أو اللي فاتورته لسه ما اتدفعتش، ما ينفعش يتنقل.
7. **الطلبات القديمة:** طلبات النقل اللي في جدول `Request` القديم (أنواعها اسمها «نقل…») بتتنقل وقت النقل، والمكتمل منها بيغيّر المالك فعليًا.

## لوجو الشعار

1. **الرفع:** المالك يرفع لوجو لكل شعار يملكه، بصيغة PNG أو JPG أو WebP وبحجم أقصى 2 ميجا. صيغة SVG مرفوضة لأنها ممكن تحمل سكربتات.
2. **الاعتماد:** اللجنة بتراجع اللوجو بصلاحية `names.logos`. بعد الاعتماد بيظهر في سجل الأسماء على `GET /api/names/{id}/logo`.
3. **الاستبدال:** لو المالك رفع لوجو جديد، القديم بيختفي لحد ما الجديد يتعتمد.
4. **اللوجوهات القديمة:** صور `Name_Logo` بتتنقل لما تمرر `--files` بمسار فولدر الموقع القديم.

## المحفظة للضمانات فقط

- **من المحفظة:** ضمان طلب الشعار وضمان دخول المزاد بس.
- **من قنوات الدفع (البطاقة) بس:** الفواتير وقيمة الشعار والشراء الفوري ورسوم دراسة الاستثمار ورسوم النقل.
- **إزاي بيتطبق:** الخادم بيرفض أي خصم من المحفظة لعملية من دول، إلا لو فيه دفعة بطاقة مدفوعة لنفس العملية بالظبط (`Money.DebitByCardAsync`).
- **الاسترداد:** المبالغ اللي بترجع (ضمانات أو رسوم) بتنزل في المحفظة، والمالك يقدر يطلب تحويلها لحسابه البنكي.

## الاسترداد للحساب البنكي (تحويل مباشر)

1. **طلب المالك:** المالك يطلب استرداد رصيده لحسابه البنكي المعتمد.
2. **قرار الموظف:** الموظف يضغط «موافقة وتحويل مباشر»، والمنصة بتبعت الفلوس للآيبان عن طريق بوابة التحويل (`IPayoutGateway`).
3. **متابعة التحويل:** لو البنك لسه بيعالج التحويل بتبقى حالته `processing`، والـ sweeper بيتابعها تلقائيًا. لو التحويل فشل، الطلب بيرجع لـ «قيد التنفيذ» ومعاه سبب الفشل.
4. **البوابة الحالية:** حاليًا شغالة محاكاة (لما `Payments:Simulate` يبقى مفعّل)، وغير كده التحويل يدوي برقم الحوالة. ربط HyperPay مستني توثيق واجهة التحويلات (HyperSplit) وبيانات الحساب.

## الدفع الإلكتروني (HyperPay)

المنصة مربوطة بـ HyperPay عن طريق COPYandPAY، وبتشتغل أول ما تحط بيانات الحساب في الإعدادات (user-secrets أو متغيرات البيئة). البيانات دي ما تتحطش في المستودع أبدًا.

```json
"Payments": {
  "Simulate": false,
  "Provider": "hyperpay",
  "PublicApiUrl": "https://api.sammha.ico.org.sa",
  "HyperPay": {
    "BaseUrl": "https://eu-test.oppwa.com/",
    "AccessToken": "…",
    "EntityId": "… (فيزا وماستركارد)",
    "MadaEntityId": "… (مدى)",
    "ApplePayEntityId": "… (Apple Pay)",
    "TestMode": "EXTERNAL"
  }
}
```

- **البيئة الحقيقية:** `BaseUrl` يتغير لـ `https://eu-prod.oppwa.com/`، و`TestMode` يتساب فاضي.
- **الخطوات:**
  1. المالك يختار وسيلة الدفع، والخادم يجهّز checkout بالـ entity بتاعها.
  2. المالك بيتحول لصفحة الدفع `GET /api/payments/hyperpay/{id}/form`، وفيها نموذج HyperPay.
  3. HyperPay يرجّع المالك على `/api/payments/hyperpay/return`.
  4. الخادم يسأل HyperPay عن نتيجة الدفع، ويقارن المبلغ والعملة ورقم العملية.
  5. لو الدفع نجح، المبلغ ينضاف للمحفظة والعملية تكمل (فاتورة أو ضمان أو رسوم…)، والمالك يرجع للصفحة اللي كان فيها.
- **وسائل الدفع:** الوسيلة اللي ملهاش entity id ما بتظهرش للمالك.
